Working on a server

Add a host as a target, then open terminals, coding agents, files, search and review on it, with sessions that keep running there when you disconnect.

Working on a server

Kyon works on another machine over SSH as it does on this Mac: terminals, coding agents, the explorer and editor, search and review all run against the host's files, with the host's tools. Shells and agents there keep running when the connection drops or you quit.

Everything starts from a target: a host, the command that connects to it, and where to start. Saved targets appear beside this machine wherever Kyon asks where to run something.

Add a host

A target uses your existing SSH setup, so your ports, keys and jump hosts work as in a terminal.

  1. Click the globe in the title bar, or choose Show remote connections from the File menu or the command palette (⌘P). The Connections dropdown opens.
  2. Click Add target and fill in the form:
    • Name: what the target is called in menus and lists. It cannot contain a dot.
    • Host: what you would type after ssh, such as user@host or an alias from ~/.ssh/config. An alias is the best choice, because it carries your port, key and jump host.
    • Before connecting (optional): a command to run on this Mac first, such as refreshing a certificate.
    • Connection command (optional): how to connect, with {host} where the host goes. Empty means ssh {host}. Use it for a wrapper or a provider's helper; without {host} in it, Host may stay empty.
    • Default working directory (optional): where terminals and agents start on the host, such as /srv/app.
    • Launch Claude Code with, and likewise for Codex, Gemini, OpenCode and pi (optional): a program that starts that agent on this host instead of its usual command.
  3. Click Save target.

Authentication is left to SSH. Kyon refuses to save a private key, a password in an address, or a flag such as --token followed by the secret itself, and asks you to confirm anything that looks like a credential (Save anyway). Commands run as one program and its arguments; for anything with pipes or ;, write a script and name it.

Each target row has Edit, Duplicate, arrows to reorder, and Remove. Targets are kept in your settings file, under Settings › System › Kyonify in the Remote targets section, where Manage targets opens the same dropdown.

How Kyon signs in

The form's Kyon's own connection choice decides how the login happens:

  • Automatic: signs in from the connections panel, and every pane on the host shares that one login.
  • Share the connection: asks the connection command for a shared SSH connection and uses it. The command has to pass -o options on to ssh.
  • Take over the terminal's connection: takes over the connection a terminal made. It works with any command, but cannot confirm the host was reached, so a slow login can look finished.

When a host asks for a password, a code or a browser sign-in, the dropdown shows its prompt in a small terminal to answer, with links you can click. A host you reach with a key asks nothing.

What gets installed on the host

Kyon talks to a host through a small helper program it brings with it, so you have nothing to install by hand.

The first time you connect, Kyon copies the helper matching the host's system to ~/.cache/kyon/orb-… on the host, named after the build. By default it asks first: a notice says Kyon's host helper is not on this machine yet, with an Install it button. Later connections reuse the copy; a newer Kyon brings its own and replaces an older one without asking, and copies no build has used for 14 days are cleared away.

Also under ~/.cache/kyon/ on the host: sessions, where the host keeps track of your running shells, and pasted, which holds files you drop onto a terminal there.

The Install SSH extension setting (Settings › System › Kyonify, SSH section) chooses ask, always or never. With never, Kyon uses an orb already on the host's path.

Supported hosts

Linux on x86-64 or ARM64 (the helper is a static build, so any distribution works) and macOS on Apple silicon or Intel. For any other system, connecting stops saying no helper is built for it.

Open a terminal or an agent on the host

Every new session can run on this Mac or on any target, chosen as you open it.

  1. Open the New session menu with ⌃⌘T, or the new-tab button.
  2. Choose Terminal or a coding agent (Claude Code, Codex, Gemini, OpenCode or pi). A panel beside it lists Local, each target, and Manage targets…. The place you used last is selected first.
  3. Pick the target. A terminal opens straight away. For an agent, Kyon asks which folder to start in, offering the target's default working directory, folders on the host as you type a path, and folders you used there before; choose Launch Claude Code in … on name (or the agent you picked).

If the host isn't connected yet, the pane says Waiting for the login to … and starts once connected; panes waiting on one host share one login.

Opening a session on a host also points the window at it, so ⌘T opens further terminals there. Agents on a host work as they do here, and Kyon offers its plugins for them once per host; see Coding agents.

Files, search and review on the host

The explorer, editor, search and review follow the session in front, so with a host's tab focused they all work on that host.

  • Browse files (⌘E) and Open a file (⌘O) list the host's tree. Files open in the editor and save back to the host. Language servers for those files run on the host.
  • Search the workspace (⌘⇧F) searches the host's files on the host.
  • Review changes (⌘R) shows the host repository's changes. Committing, pushing and opening a pull request run with the host's git.

To point the window at a machine without opening a session, run Read from another machine from the File menu or the palette and pick a host, or this machine to come back.

While a host is away, its open files say so and can't be edited; what you typed is kept, and a file changed on the host meanwhile is read again.

Working in a host's terminal

A terminal on a target behaves like one on this Mac.

  • Blocks and the input: with Kyonify SSH Sessions on (the default), shells on hosts get Kyon's blocks and input. It applies to shells opened after you change it.
  • Completion: Tab completes paths and directories from the host's files.
  • The directory chip shows ~ for your home directory on the host.
  • Typing appears at once, before the host echoes it back.
  • Dropping files: drop a file from Finder onto the terminal and Kyon copies it to the host, showing Sending name to the host with the percentage done, then types the path it has on the host into the prompt, or into Rich Input if that is open. Any size works; folders can't be sent. Copies are kept in ~/.cache/kyon/pasted for a day, at most 50 at a time.

A host Kyon serves, and ssh typed in a terminal

Running ssh yourself in a local terminal gives a plain shell at the far end. For blocks, host completion, kept sessions and file drops, add the machine as a target and open the terminal from the New session menu.

Sessions that keep running

Shells and agents on a host keep running when your connection drops or you quit Kyon, so a long build or a working agent carries on without you.

When you quit with tabs open, Kyon asks (unless you have told it not to): Quit ends the shells and the tabs come back with new ones, while Keep Shells and Quit leaves them running. With Restore the last session on, the next launch puts each terminal back on the host it was on, attached to the same shell, sized to its pane.

The Connections dropdown lists the sessions kept on this Mac, then on each connected target, with each one's folder and state: In tab "…" (click to go there), Open elsewhere (attached in another window or another Kyon), Left … ago (running, nobody on it), or Not running · starts again when opened.

Click End, then Confirm end, to stop one; closing its tab does the same. Unattached sessions end after the days set in End sessions left alone for (7 by default; 0 keeps them).

When the connection drops

A dropped connection repairs itself, and nothing you type is lost.

The target's row in the dropdown turns to Reconnecting and the terminal says it is reconnecting. Kyon retries with growing pauses for about two minutes; once through, the terminal shows [reconnected] in the same shell. What you typed meanwhile is held, the pane says Not sent yet … it goes once the connection is back, and it is sent once it can be. Keys typed into a terminal that has no shell yet are refused and the pane says they were not sent.

If the host stays away, Kyon stops trying and the row offers Reconnect; panes waiting on it say Not connected to … with a Connect link. Turn off Reconnect dropped sessions to have terminals end instead.

When the host restarted

A host that restarts loses its shells and everything running in them. Once you are connected again, each terminal that was open on it comes back as a new shell in the same folder, taking what you type once that shell is at its prompt, and a coding agent that was running there goes on with its conversation, as it does when Kyon itself is restarted. Connect on a host Kyon gave up on reconnects the terminals already open there; it does not start them over.

Where a terminal you signed in from carries the connection, that terminal ends with the restart. The terminals on the host wait, saying they are reconnecting, until you connect again; the new sign-in then carries them all.

Disconnect or remove a host

You can close a connection or forget a target without touching the host itself.

  • Disconnect, then Confirm disconnect, closes the connection. Every shell and agent on it ends. The target stays saved.
  • Remove, then Confirm remove, deletes the target from your settings. It changes nothing in your SSH config, credentials or on the host, and stops nothing running there. A window reading from that host goes back to this machine.

Limits

Indexing and MCP servers are this machine's only. Codebase indexing and the MCP servers set up in Kyon work on this Mac, not on a host.

One person per session. When a second Kyon attaches to a session, the first is displaced.

Signing in from a terminal. A terminal that signs in to a host stays a plain shell at the far end. An agent launched on a host you sign in to in a terminal gets that sign-in in a tab of its own, and starts in a shell the host serves once the sign-in completes.

Search on a host. The docked search doesn't say a host is still connecting, shows a host's results all at once at the end (at most 20,000 lines), and searches one machine at a time.

The explorer on a host reaches the tree the host was started for, plus your home and temporary directories there, and nothing further.

Omnigent on a host has been tested only against a stand-in server, not a real one.
